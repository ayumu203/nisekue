# アイテム機能設計

## 1. 目的

本ドキュメントは、以下の Issue を実装するための仕様を整理する。

* `feat: 【アイテム】アイテム管理の実装`
* `feat: 【アイテム】合成機能の実装`
* `feat: 【アイテム】売却·購入機能の実装`
* `feat: 【訓練】熟練度上昇処理の実装`
* `feat: 【アイテム】ステージクリア報酬の装備の実装`

既存の `docs/MKD05_装備機能仕様ドラフト.md` で定義した装備個体の考え方を維持しつつ、プレイヤーが扱う所持品全体を「アイテム管理」として定義する。

## 2. スコープ

今回の設計でスコープ内とするのは以下。

* プレイヤー所持アイテムの上限管理
* アイテム一覧表示
* 装備 / 使用 / 合成 / 売却 / 削除
* 他プレイヤーによるマーケット購入
* 他プレイヤーへのプレゼント送信
* 売却期限切れアイテムの削除
* マーケットカテゴリフィルタ
* 訓練実行時の武器熟練度上昇
* クエスト成功時の装備報酬付与
* クエスト成功時の消費アイテム報酬付与

今回の設計でスコープ外とするのは以下。

* アイテム郵便箱や保管倉庫
* 売買履歴の詳細検索
* オークション形式の入札
* 装備熟練度の戦闘計算反映
* NPC 店舗による固定価格販売

## 3. 用語

### 3.1 アイテム種別

アイテム管理では以下の 2 系統を扱う。

* `EquipmentItem`
  * 既存の `Equipment` / `PlayerEquipment` に相当する武器・防具。
  * 個体ごとに耐久値、熟練度、装備状態を持つ。
* `ConsumableItem`
  * 使用時に効果を発揮して消費されるアイテム。
  * 同一アイテムはスタック可能とする。
  * 主用途は `基礎ステータス上昇` と `特定ジョブへの転職` とする。
  * 将来的に特定マップ解放などへ拡張する余地は残すが、今回はスコープ外とする。

### 3.2 所持枠

* プレイヤーが同時に保有できるアイテム枠は `20` とする。
* 枠は「スタック数」ではなく「一覧上の所持スロット数」で数える。
* `PlayerEquipment` 1 個体は `1` 枠とする。
* `ConsumableItem` は同一 `ItemId` ごとに 1 スタックへ集約し、そのスタックで `1` 枠とする。
* 装備中の `PlayerEquipment` は所持枠に含めない。
* マーケットへ出品したアイテムはプレイヤー所持一覧から外し、所持枠には含めない。

### 3.3 フレーバーテキスト

* 装備・消費アイテムともに、ゲーム内説明文として `FlavorText` を持てるようにする。
* `FlavorText` は戦闘計算には使用しない。
* 熟練度上限 `MasteryCap` と合成必要 Gold `SynthesisGoldCost` は装備 CSV で管理する。

### 3.4 効果量

マーケット一覧で表示する「効果量」は以下のように扱う。

* 武器・防具: `StatusBonus` の要約値
* 消費アイテム: 使用時に反映される補正量
  * 固定値上昇は `StatusBonus`
  * 割合上昇は `StatusBonusPercent`
  * 割合上昇は、使用時点のプレイヤー基礎ステータスに対して `ceil(現在値 * 割合 / 100)` を恒久加算する

## 4. 設計方針

### 4.1 アイテム管理画面の責務

アイテム管理画面は、プレイヤーが現在所有しているアイテムに対して以下を行う入口とする。

* 装備変更
* 消費アイテムの使用
* 同名装備の合成
* マーケットへの出品
* 不要アイテムの削除

一覧取得時には、少なくとも以下の情報を返す。

* アイテム種別
* 一覧表示名
* アイコン画像
* フレーバーテキスト
* 所持数
* 個体 ID
* 装備状態
* 耐久値 / 最大耐久値
* 熟練度
* 効果量表示
* 売却可否
* 使用可否

### 4.2 マスタと個体の分離

既存装備設計と同様に、マスタデータとプレイヤー所持データは分離する。

* 装備は `Equipment` をマスタ、`PlayerEquipment` を個体とする。
* 消費アイテムは `Item` をマスタ、`PlayerItemStack` をプレイヤー所持スタックとする。
* アイテム管理 API はこれらをそのまま返さず、共通 ViewModel に射影する。

### 4.3 Gold の導入

売却・購入を成立させるため、プレイヤー恒久情報に `Gold` を追加する。

* 売却時に Gold は増えない。
* 出品アイテムが購入成立した時点で、販売者へ `価格 * 数量` の Gold を加算する。
* 購入時は購入者の Gold を即時減算する。
* Gold 不足時は購入不可とする。

## 5. アイテム管理仕様

### 5.1 一覧表示

* アイテム一覧は認証済みプレイヤーのみ取得可能とする。
* 一覧は「装備中」「所持」「出品中」を別タブまたは別 API で分離してよい。
* 装備中一覧には、武器 1 件、防具 1 件の現在装備を表示する。
* 所持一覧には、出品中ではない `PlayerEquipment` と `PlayerItemStack` を表示する。
* 出品中一覧には、自分がマーケットへ登録した販売中アイテムを表示する。

### 5.2 装備

* 装備操作は `EquipmentItem` のみ対象とする。
* 武器は `1` スロット、防具は `1` スロットとする。
* すでに同種別の装備を装備中の場合、新しい装備を装備する際に既存装備を `Inventory` へ戻す。
* `Broken` 状態の装備は装備できない。
* 現在職業で装備不可能な装備は装備できない。
* マーケット出品中の装備は装備できない。

### 5.3 使用

* 使用操作は `ConsumableItem` のみ対象とする。
* 使用時は定義済み効果をプレイヤーへ反映し、使用数分だけスタックを減算する。
* 初期スコープでは `HP回復` `MP回復` `蘇生` `一時バフ` は実装しない。
* 初期スコープの消費アイテム効果は `基礎ステータス上昇` と `転職` に限定する。
* `基礎ステータス上昇` は固定値上昇と割合上昇の両方を定義できる。
* 割合上昇は `MaxHp` `MaxMp` `Strength` `Defense` `Intelligence` `Luck` `Speed` を対象にできる。
* 割合上昇量は 1 回使用ごとに個別計算し、複数個使用時はその都度更新後の基礎ステータスをもとに繰り返し加算する。
* 転職アイテムには `必要レベル` と `必要マスター済みジョブ` を持たせる。
* 転職アイテム使用時、条件を満たしていれば即時にジョブを変更する。
* ジョブ変更画面（`PUT /player/job`）では見習い / 戦士 / 盾使い / 魔法使い / 僧侶 / レンジャーへの変更を許可する。
* ランジャーは通常転職で選べる基本職として扱い、Sniper / TrapMaster / 鬼武者などの上位職への遷移は転職アイテムによる使用時のみ有効とする。
* 転職アイテムは遷移先ジョブを明示しておき、フロントエンド側で通常転職対象外ジョブのみアイテム経由で選択肢に出るよう制御する。
* 使用後に数量が `0` になったスタックは削除する。
* 戦闘中クエストや特訓実行中は、別途戦闘設計で明示していない限りアイテム使用不可とする。

### 5.4 合成

合成は「同一 `EquipmentId` の装備を素材として消費し、装備中個体の耐久値を回復する」機能として定義する。

* 合成対象は `EquipmentItem` のみとする。
* 素材にできるのは `Inventory` 状態の装備のみとする。
* 回復先にできるのは、同一プレイヤーが現在装備中の同一 `EquipmentId` の装備のみとする。
* 武器は武器へ、防具は防具へのみ合成できる。
* 素材装備の `Durability` が `1` 以上であることを必須とする。
* 回復量は「素材装備の現在耐久値の 1/3 を切り上げた値」とする。
* 回復後の耐久値は `対象装備の MaxDurability` を上限とする。
* 合成成功時、素材装備は削除する。
* 装備中に同一名称装備が存在しない場合は合成不可とする。
* `Broken` な素材装備は合成素材に使用できない。
* `Broken` な装備は回復先にも使用できない。
* `Broken` な装備は破棄のみ可能とする。
* 合成には各装備ごとに定めた Gold を要求する。

例:

* 装備中の `銅の剣` の耐久値が `3 / 10`
* 所持中の `銅の剣` の耐久値が `4 / 10`
* 回復量は `ceil(4 / 3) = 2`
* 合成後、装備中は `5 / 10` となり、素材側は削除される

### 5.5 売却

* 売却はアイテム管理画面から行う。
* 売却対象は `Inventory` 状態の装備、または `PlayerItemStack` の所持分とする。
* 装備中アイテムは売却不可とし、売却前に外す必要がある。
* 売却時には `販売数` と `単価` を指定する。
* `PlayerEquipment` の販売数は常に `1` とする。
* `PlayerItemStack` は `1` 以上 `所持数以下` の販売数を指定できる。
* 単価は `1` 以上の整数 Gold とする。
* 売却登録時点で対象アイテムはプレイヤー所持から取り除き、販売在庫へ移す。
* 売却登録後、販売期限は `出品日時 + 15日` とする。
* 期限までに購入されなかった残在庫は自動削除し、プレイヤーへ返却しない。
* アイテム管理画面で `出品` を押した後は、そのカードの通常操作ボタンをすべて非表示にし、`確定` と `取消` のみ表示する。
* 同時に編集できる出品カードは 1 件のみとし、別カードで `出品` を押した場合は前の編集中状態を閉じる。

### 5.6 削除

* 削除はマーケットへ出さずに所持品を破棄する操作とする。
* 装備中アイテムは削除不可とし、削除前に外す必要がある。
* `PlayerEquipment` は個体単位で削除する。
* `PlayerItemStack` は指定数だけ減算してよい。
* 数量が `0` になったスタックは削除する。

### 5.7 プレゼント

* プレゼントは他プレイヤーのチャットページから実行する。
* 送信対象は `Inventory` 状態の装備、または `PlayerItemStack` の所持分とする。
* 自分自身への送信は禁止する。
* 装備中アイテムは送信不可とし、送信前に外す必要がある。
* `PlayerEquipment` の送信数は常に `1` とする。
* `PlayerItemStack` は `1` 以上 `所持数以下` の数量を指定できる。
* 送信時はトランザクション内で送信者・受信者・対象在庫をロックし、二重送信や無限増殖を防止する。
* 受信者の所持枠が不足する場合、送信は失敗とする。
* 消費アイテムは受信者の既存スタックへ加算し、未所持なら新規スタックを作成する。
* 装備は所有者を受信者へ移し、状態は `Inventory` とする。
* 送信成功時、受信者チャットへ `system message` を 1 件追加する。

## 6. マーケット仕様

### 6.1 出品データ

マーケットでは、プレイヤー所持から切り離した販売データを保持する。

* `MarketListing`
  * 出品 ID
  * 販売者 `PlayerId`
  * 販売者名
  * 販売者アイコン
  * アイテム種別
  * アイテムマスタ ID
  * アイテム表示名
  * 効果量表示
  * 販売数量
  * 残数量
  * 単価
  * 登録日時
  * 期限日時

装備出品時は、購入者へそのまま装備個体を移管する。
そのため装備販売データには、対象 `PlayerEquipmentId` または装備個体復元に必要な属性を保持する。

### 6.2 一覧表示

他プレイヤーが閲覧できるマーケット一覧には、少なくとも以下を含める。

* アイテム名称
* 効果量
* 販売者名
* 販売者アイコン
* 単価
* 残数量
* 期限日時
* カテゴリ

* カテゴリは `Weapon | Armor | Item | Map` の 4 種とする。
* 装備は `equipmentType` から `Weapon` / `Armor` を導出する。
* 消費アイテムは宝の地図 ID 一覧に含まれるものを `Map`、それ以外を `Item` として導出する。
* マーケット画面ではカテゴリフィルタと文字列検索を併用できるようにする。

### 6.3 購入

* 購入は認証済みプレイヤーのみ可能とする。
* 自分自身が出品したアイテムは購入不可とする。
* 購入は即時確定とする。
* 購入要求時に、販売中かつ期限切れでないことを検証する。
* 購入要求時に、購入者 Gold が `単価 * 購入数` 以上あることを検証する。
* 購入要求時に、購入後の所持枠が `20` を超えないことを検証する。
* 装備購入時は装備個体を購入者へ移管し、状態は `Inventory` とする。
* 消費アイテム購入時は購入者スタックへ加算する。
* 購入成立時、購入者 Gold を減算し、販売者 Gold を増算する。
* 購入成立時、販売者の既存チャットルームへ `system message` として売却成立メッセージを送信する。
* 残数量が `0` になった出品は販売完了として削除する。

### 6.4 期限切れ削除

* `期限日時 < 現在時刻` の出品は期限切れとする。
* 期限切れ処理は GitHub Actions の定期バッチで実行する。
* GitHub Actions からはサーバーの内部メンテナンス API を呼び出して削除処理を起動する。
* 内部メンテナンス API は GitHub Secrets で管理する専用トークン付きリクエストのみ受け付ける。
* 期限切れで残っていたアイテムは削除し、販売者へ返却しない。
* 期限切れで削除した件数はレスポンスで確認できるようにし、ワークフローのログへ残す。
* 期限切れで削除したアイテムは `item_delete_logs` へ `expired_listing_cleanup` 理由で記録する。
* 期限切れ出品は一覧表示から除外する。

## 7. 訓練時の武器熟練度上昇

### 7.1 上昇条件

* 特訓完了時、装備中の武器が存在し `Broken` でない場合、その武器個体の熟練度上昇可否を判定する。
* 勝敗にかかわらず、特訓 API が正常に戦闘解決まで完了した場合は判定対象とする。
* 防具の熟練度は今回の Issue では上昇させない。
* 熟練度は「プレイヤーレベルと敵レベルの差の絶対値が `(プレイヤーレベル / 5) + 5` 以下の場合のみ `+1`、それ以外は `+0`」とする。
* 各装備は熟練度上限を持ち、その上限を超えては上昇しない。

### 7.2 他処理との順序

特訓終了時の保存順序は以下とする。

1. 戦闘結果と経験値を確定する
2. 武器熟練度上昇可否を判定し、必要なら `+1` する
3. 装備中の武器・防具耐久値をそれぞれ `1` 消費する
4. プレイヤー更新と装備更新を保存する

### 7.3 熟練度の役割

* 熟練度は引き続き装備個体単位で保持する。
* UI 上では熟練度を数値で表示する。
* 装備中武器の熟練度は、装備マスタが持つ基本ステータス補正へ反映する。
* 熟練度 `10` ごとに、武器の装備補正値へ `+1%` を加算する。
* 熟練度補正は `floor(装備補正値 * (熟練度 / 10) / 100)` で算出し、基本補正値へ加算する。
* 熟練度補正の対象は武器のみとし、防具には適用しない。
* 熟練度を装備マスタ単位へ移す予定は持たない。

## 8. ステージクリア報酬の装備

### 8.1 報酬の考え方

* クエスト成功時、ステージ定義に応じて装備報酬を抽選付与できるようにする。
* 報酬はステージごとの CSV ドロップテーブルで定義する。
* 初期スコープでは「1 つの共通抽選結果をパーティ全員へ適用する」方式とする。
* パーティ内に `大盗賊` が 1 人でもいる場合、共通抽選を 2 回行い、どちらかで当たりならその当たり結果を全員へ適用する。
* `大盗賊` が複数いても追加抽選回数は増やさない。
* ハズレを含む抽選とし、初期目安は `75%` 程度とする。
* 報酬装備は `PlayerEquipment` 個体として生成し、`Inventory` 状態で付与する。

### 8.2 付与タイミング

* 報酬付与は `QuestRun` の成功確定後、耐久値消費処理の後に行う。
* 付与された報酬装備は、進行中クエストには影響しない。

### 8.3 所持上限超過時

* クエスト成功時点で所持枠に空きがない場合、その装備報酬は付与しない。
* 付与できなかった報酬は破棄し、クエスト結果レスポンスに `inventoryFullSkippedRewards` として返す。
* 初期スコープでは、報酬保留箱や後日受取機能は持たない。
* 将来的に救済導線を追加する余地は残す。

## 9. API 仕様案

### 9.1 アイテム一覧取得

* `GET /items`
* 認証必須
* レスポンスは `capacity`, `usedSlots`, `equippedItems`, `inventoryItems` を持つ

### 9.2 アイテム使用

* `POST /items/{itemStackId}/use`
* 認証必須
* 消費アイテムのみ対象
* リクエストで使用数を受け取る

### 9.3 装備変更

* 既存の装備変更 API を継続利用してよい
* もしくは `POST /items/equipments/{playerEquipmentId}/equip` を追加してよい

### 9.4 合成

* `POST /items/equipments/{playerEquipmentId}/synthesize`
* 認証必須
* `playerEquipmentId` は素材側の装備個体 ID とする
* レスポンスには回復対象装備の更新後耐久値を含める

### 9.5 売却登録

* `POST /market/listings`
* 認証必須
* リクエストは `itemType`, `playerEquipmentId?`, `itemStackId?`, `quantity`, `unitPrice` を持つ

### 9.6 マーケット一覧取得

* `GET /market/listings`
* 認証必須
* フィルタは将来拡張として `itemType`, `sellerName`, `sort` を受け取ってよい

### 9.7 自分の出品一覧取得

* `GET /market/my-listings`
* 認証必須

### 9.8 購入

* `POST /market/listings/{listingId}/purchase`
* 認証必須
* リクエストは `quantity` を持つ
* 装備出品では `quantity = 1` 固定とする

### 9.9 削除

* `DELETE /items/equipments/{playerEquipmentId}`
* `DELETE /items/stacks/{itemStackId}`
* 認証必須

## 10. バリデーション

* 所持枠 `20` を超えるアイテム付与・購入・受取は不可
* `Broken` 装備は装備不可・合成素材不可・回復先不可・削除のみ可
* 装備中アイテムは売却不可・削除不可

* 売却数量・購入数量・使用数量・削除数量は `1` 以上
* 出品期限は登録から `15日` 固定

## 13. 未確定な点・整理すべき仕様

以下は、実装前に整理した論点と今回の回答である。

### 13.1 消費アイテムの初期スコープ

* 今回の Issue では消費アイテムも含む。
* 初期スコープは `基礎ステータス上昇` と `特定ジョブへの転職` のみとする。
* `HP回復` `MP回復` `蘇生` `一時バフ` は今回実装しない。
* 消費アイテムはホーム画面系のアイテム管理からのみ使用する。

### 13.2 所持枠 20 の厳密な数え方

* 消費アイテムのスタック上限は `99` とする。
* 同一消費アイテムが複数スタックに分かれるケースは許容しない。
* クエスト報酬や購入時に、既存スタックへ加算できる場合は枠消費 `0` とみなす。
* 装備中装備は所持枠に含めない。

### 13.3 合成ルールの詳細

* 合成対象は「同一 `EquipmentId`」で判定する。
* 回復先は装備中個体のみとする。
* 合成時は熟練度を引き継がず、耐久値のみ回復する。
* `Broken` 装備は回復先として許可しない。
* `Broken` 装備は破棄のみ可能とする。
* 合成には各装備ごとに定めた Gold を要求する。

### 13.4 売却価格と相場ルール

* 売価は完全自由入力とする。
* 装備の耐久値や熟練度は価格計算へ自動反映しない。
* 販売手数料は取らない。
* 購入時に販売者へ Gold を即時付与する。
* 購入成立時、販売者のチャットページへ通知メッセージを送る。

### 13.5 期限切れ時の扱い

* 期限切れアイテムは完全削除とする。
* 期限切れ出品に対する通知は出さない。
* 期限判定は GitHub Actions の定期バッチで実行する。

### 13.6 購入時の競合制御

* 同一出品へ同時購入が来た場合、購入処理中は対象出品行をロックし、他プレイヤーが介入できないようにする。
* 装備個体販売とスタック販売は同一テーブルで扱う。
* 購入失敗時のエラーは少なくとも以下に統一する。
  * `404 NotFound`: 出品が存在しない、または販売終了済み
  * `409 Conflict`: 同時購入競合で残数が変化した
  * `400 BadRequest`: 数量不正、自分の出品を購入しようとした
  * `422 UnprocessableEntity`: Gold 不足、所持枠不足、期限切れ
* ここでいう「統一」は、同じ失敗理由に対して API ごとに違う文言へぶれさせず、クライアントが同じ理由として扱えるようにすることを指す。

### 13.7 Gold の導入範囲

* `Gold` は `Player` 集約へ持たせ、今回の Issue に含める。
* 初期 Gold は `100` 配布する。
* クエスト報酬 Gold とマーケット Gold は同一通貨とする。

### 13.8 特訓で上昇する熟練度の対象

* 熟練度上昇対象は武器のみとする。
* 特訓敗北時にも熟練度上昇判定を行う。
* 1 回の特訓で「レベル差の絶対値が `(プレイヤーレベル / 5) + 5` 以下の場合のみ `+1`、それ以外は `0`」とする。
* 熟練度上限は各装備ごとに持つ。

### 13.9 熟練度の将来効果との整合

* 熟練度は将来的に基本ステータスへ反映する。
* 熟練度は装備個体単位で持ち続け、装備マスタ単位へは移さない。
* UI 上では数値で見せる。

### 13.10 ステージ報酬装備の抽選方式

* ステージごとに CSV の候補テーブルから抽選する。
* ハズレを含み、初期目安は `75%` 程度とする。
* マルチプレイ成功時は全員に同一報酬を配る。
* `大盗賊` がいる場合も「全員に同一報酬」の原則は維持し、個別抽選へはしない。
* ドロップ率は今回の仕様に含める。
* レア度は今回の仕様に含めない。

### 13.15 ステージクリア報酬の消費アイテム

* ステージごとに `stage_item_rewards.csv` を追加し、消費アイテム報酬を定義する。
* 装備報酬の `stage_equipment_rewards.csv` は装備専用のままとし、アイテムを混在させない。
* アイテム報酬も「1つの共通抽選結果をパーティ全員へ適用する」方式とする。
* `大盗賊` がいる場合、アイテム報酬も装備報酬と同様に共通抽選を2回行い、どちらかで当たりなら当たりとする。
* アイテム報酬は既存スタックがあれば加算し、ない場合のみ新しい `PlayerItemStack` を作成する。
* 既存スタックが満杯で加算できないケースは初期スコープでは発生しない。`MaxStack` を上限とする補充が必要になった時点で別途再設計する。
* 新規スタックが必要で所持枠が足りない場合、そのプレイヤーへのアイテム報酬付与はスキップし、既存の `inventoryFullSkippedPlayerIds` へ含める。

### 13.11 所持上限超過時の報酬救済

* 所持枠不足時の報酬は破棄する。
* 保留箱やプレゼントボックスは後続 Issue とする。
* ステージ報酬だけ特別に枠超過を許容しない。
* 将来的に救済導線を追加する余地は残す。

### 13.12 API と画面の責務分担

* 出品中一覧は `GET /market/my-listings` として分ける。
* アイテム一覧は既存のプレイヤー取得 API に含めず、アイテム専用 API に分離する。
* 画面上では「装備管理」と「アイテム管理」を分けない。

### 13.13 監査・履歴

* 売買履歴は今回保存する。
* アイテム削除ログは保存し、`10日` で削除する。
* GM / 管理者向けの追跡要件は持たない。
* 売買履歴の保持項目は `sellerId`, `buyerId`, `itemId`, `quantity`, `unitPrice`, `purchasedAt` とする。
* 削除ログも最低限同等の識別ができる項目を保持する。

### 13.14 マイグレーションと既存データ移行

* 既存 `PlayerEquipment` データはそのままアイテム管理の装備一覧へ取り込む。
* つまり、新しい共通アイテムテーブルへ移し替えるのではなく、既存 `PlayerEquipment` を装備系アイテムとして画面・API で束ねて扱う。
* `Gold` 追加時、既存プレイヤーには一括で `100 Gold` を初期配布する。
* マーケット導入後の検索系インデックスと期限切れ削除ジョブは必要である。
* 期限切れ削除ジョブは GitHub Actions の定期実行で対応し、アプリ側の内部メンテナンス API を叩く。
* GitHub Actions 側では既存の `VITE_API_BASE_URL` を利用し、`MARKET_CLEANUP_TOKEN` のみ Secrets として追加する。
* 装備ごとの `MasteryCap` と `SynthesisGoldCost` は CSV に追加し、既存装備 CSV を拡張して管理する。
* 転職アイテムの `必要レベル` `必要マスター済みジョブ` `遷移先ジョブ` もアイテム CSV に持たせる。

## 14. 今回の確定事項

1. プレイヤーの所持枠は `20` とし、装備中装備は枠に含めない。
2. マーケット出品中アイテムは所持枠から外す。
3. 合成は「同一 `EquipmentId` の所持装備を素材にして、装備中装備の耐久値を回復する」機能とする。
4. 合成時の回復量は素材耐久値の `1/3` 切り上げとし、素材は消滅する。
5. 売却は登録時点で所持品から切り離し、未購入の残在庫は `15日` 後に削除する。
6. 購入は即時確定で、購入時に Gold と所持枠を検証する。
7. 購入成立時、販売者へ Gold を即時付与し、チャットページへ通知を送る。
8. 特訓完了時、レベル差の絶対値が `(プレイヤーレベル / 5) + 5` 以下の場合のみ装備中武器の熟練度を上昇させる。
9. クエスト成功時、ステージごとの CSV ドロップテーブルから共通報酬を抽選し、`Inventory` 状態で付与する。
10. 報酬付与時に所持枠が足りない場合、報酬は付与せず結果表示のみ行う。
11. `MasteryCap` と `SynthesisGoldCost` は装備 CSV、転職条件はアイテム CSV で管理する。
12. 売買履歴と削除ログを保存する。
