# 名鑑の祠 設計

プレイヤーが敵として出現するチャレンジステージ「名鑑の祠」の設計。
議論の経緯は Notion のタスクメモ「ゲーム内のプレイヤーが敵として出現するマップ」とその子ページ「名鑑の祠 詳細設計」にある。

## 1. 決定事項の一覧

- ソロ限定。推奨レベル表示は「???」、入場条件はレベル100のみ
- 敵：転生回数・レベル・戦闘指数（装備込み）の上位20人。除外なし。装備込みの実効ステータス、ペットなし。ラン開始時に全フロア分を確定
- フロア：通常4フロア（各5体）＋ボス1フロア（自分＋自分を除く上位3人）。下位から順に強くなる帯で振り分け
- 登場回数：同じフロアに同じ人は出さない。通常フロアでは2回まで、ボスフロアを含めて3回まで
- 配置：前衛＝戦士系・守護系（トリックスター以外）／中衛＝狩人系・見習い・トリックスター・ネクロマンサー／後衛＝魔法系・僧侶系（ネクロマンサー以外）。2枠を超えたら後ろの列へ
- ボスフロアの敵はボス扱い（即死技が効かない）
- ランを DB から読み直したときのボスフロア判定も、ステージ定義（stage_floors）ではなくラン開始時の計画（`mirror_enemy_plan_json` の `IsBoss`）を正とする
- フロア間の回復はなし（既存のクエストと同じ）
- 敵の行動：名鑑の祠専用の敵 AI（`MirrorEnemyActionPolicy`）。職業らしい動き＋重ねがけ防止などのガード。単体攻撃は HP が低い相手を狙う。少しランダム性を入れる。即死技は使わない。状態異常・トラップは使う。蘇生は敵1体につき1フロア3回まで（フロアが変わったら数え直し）。守護系は基本「かばう」
- 味方：最低出撃人数に足りない分を、既存のクエストと同じく `stage_npc_templates` の NPC で補充（プレイヤーからの補充は見送り。#530 を閉じた）
- 報酬なし（exp・gold・装備・アイテム・捕獲）、クールダウン3分あり、クリア回数ランキングに数えない、逃走可
- 背景：`client/public/image/quest/mirror-shrine-battlefield.svg`

## 2. 敵の選出

### 2.1 上位20人の決め方

- 並び順：転生回数 desc → レベル desc → 戦闘指数 desc → プレイヤーID（結果を安定させるためだけ）
- 戦闘指数は装備込みの実効ステータスで計算する。ランキング画面は素のステータスなので、同点のときの並びはランキング画面とずれることがある
- 戦闘指数は保存されていないので、次の手順で取る
  1. players を（転生回数 desc, レベル desc）で並べ、20番目の（転生回数, レベル）を取る
  2. その組以上のプレイヤーを全員取る（20番目と同点の人を全部含む）
  3. その人たちの装備を読み、実効ステータスと戦闘指数を計算して並べ替え、上位20人に絞る（実効ステータスはそのまま敵のスナップショットに使う）
- 上位20人はラン開始時に毎回取る。転送量が大きいと分かったらキャッシュを検討する

### 2.2 自分自身

- 自分が上位20人に入っていれば通常フロアにも出る（外さない）
- ボスフロアは自分＋「自分を除いた」上位3人
- 自分の登場回数もボスフロアを含めて3回までに数える

### 2.3 フロアへの振り分け（帯）

- 順位で帯を作る：1F＝16〜20位、2F＝11〜15位、3F＝6〜10位、4F＝1〜5位、ボス＝自分＋1〜3位
- 上位20人が変わらなければ毎回同じ構成になる

### 2.4 20人未満のとき（n 人）

- 順位の低い順のリストを、1人ずつずらしながら繰り返して通常フロアの 4×5＝20 枠を埋める。同じフロアに同じ人は入れない。通常フロアでの登場は1人2回まで
- 枠が埋まりきらなければ、そのフロアの敵を減らす（n＜5 なら1フロアの敵は n 体以下）
- ボスフロアの上位3人のうち、登場が3回を超える人は外す（その分ボスフロアの敵が減る）
- 自分以外に誰もいない場合は、通常フロアに自分を置く（3回まで）

### 2.5 列への配置

- 各フロアの敵を職業から希望列に分け、各列2枠（Left→Right）に順位の高い順で入れる
- あふれた人は一つ後ろの列の空き枠へ。後衛があふれたら空いている前の列（中衛→前衛）へ

### 2.6 敵のスナップショット

- 名前：プレイヤー名そのまま
- 画像：`image/character/〈ファイル名〉`。未設定のときは `PlayerImageCatalog.DefaultFileName`（新規プレイヤーの既定画像）
- 職業・レベル・転生回数
- ステータス：装備込みの実効ステータス（`EquipmentStatusResolver.BuildEffectiveStatus`）。開始時は HP・MP 満タン
- 技：プレイヤーの技セット（最大10枠）から即死技を除いたもの

## 3. 敵の行動（`MirrorEnemyActionPolicy`）

### 3.1 新しく作る理由

- 既存の敵 AI（`QuestEnemyActionPolicy`）はバフが「すでにかかっているか」を見ないため、自分へのバフ技を持つプレイヤーの技セットを渡すと、MP が尽きるまでバフしかしない
- ほかにも、状態異常・トラップ・MP 回復を使わない、蘇生を最優先し続ける、範囲の広さで技を選ぶ、などの問題がある
- `EnemyAiType` は定義にあるが行動の選択には使われていない
- 既存の敵 AI と味方 NPC のロジックは変えない（他のステージに影響させない）

### 3.2 共通のガード

- MP が足りない技は使わない
- バフ：同じ能力のバフがすでにかかっている相手には使わない
- 挑発：自分が挑発中なら使わない。かばう：自分がかばう状態なら使わない
- 自傷バフ（`HalveSelfHp`）：HP が20%以上のときだけ
- 状態異常：相手がすでに同じ状態異常なら使わない
- トラップ：相手側にすでにトラップがあれば使わない
- 蘇生：蘇生技を使う敵1体につき1フロア3回まで。回数は敵の状態（`QuestEnemyState.ReviveUsedCount`）に持たせるので、次のフロアには引き継がれない。蘇生を選んだ時点で1回と数える（行動前に倒されて不発でも数える）
- 自分が倒れる技（`Knockout` の対象が自分の技＝自爆）は使わない
- 即死技：技セットから除外済み
- 何も選べなければ通常攻撃、それもできなければ待機

### 3.3 攻撃技と標的

- 攻撃技は「狙える相手への見込みダメージの合計」で選ぶ（威力倍率×攻撃ステータス×ヒット数×当たる人数）。同じくらいなら MP が安い方
- 単体攻撃・単体の状態異常：挑発中の相手がいればそこ（戦闘の仕様で強制される）。いなければ現在 HP が一番低い相手。同じなら職業ごとの列の好み（前衛職は前列、魔法系・狩人系は後列）
- 範囲攻撃：当たる人数と見込みダメージの合計が最大になる位置を狙う
- 回復：HP の割合が一番低い仲間

### 3.4 職業別の優先順

- 戦士系：①自分への攻撃バフ → ②最大見込みダメージの攻撃 → ③通常攻撃
- 守護系（トリックスター含む）：①かばう（仲間の HP に関係なく、かばう状態でなければ使う）→ ②かばう技を持たないときだけ挑発 → ③仲間への防御バフ → ④攻撃
- 魔法系：①自分への知力バフ → ②狙える相手が2人以上なら範囲攻撃、1人なら単体の最大火力 → ③MP が30%以下なら MP 回復技 → ④通常攻撃
- 僧侶系（ネクロマンサー含む）：①蘇生（上限あり）→ ②HP 50%以下の仲間を回復 → ③リジェネ・防御バフ → ④攻撃
- 狩人系：①トラップ → ②状態異常 → ③単体攻撃
- 見習い：攻撃技 → 通常攻撃
- バフ・挑発などは、共通のガードで「すでにかかっている」なら飛ばして次へ
- 自分へのバフは、戦士系は力（力・知力）、魔法系は知力（力・知力）を上げる技だけを使う。対象の能力のバフが1つでもかかっていれば使わない。使える状況でも50%の確率で見送り、攻撃などほかの行動に進む（毎回の初手がバフになるのを避ける）。能力を限定しないと、バフ技を2種類以上持つ敵がかけ直しを続けて攻撃しなくなる
- 「かかっている」は上げる向きのバフだけを数える。デバフで下げられているだけならかかっていない扱い

### 3.5 ランダム性

- 第1候補とは別に第2候補を出しておき、15% の確率で第2候補を選ぶ（第2候補がなければ第1候補）
- 確率・しきい値・回数はマスタデータ `mirror_configs` で持つ（「7.1 調整値」）。本文の数値は初期値
- 乱数は差し替えられるようにして、テストでは固定する

### 3.6 確認が必要なこと

- 敵がトラップ・挑発・かばうを使ったときに戦闘が正しく解決されるかをテストで確認する。動かない技があればその技を除外する
- 味方側のトラップは `internal.quest_floor_traps`（`source_participant_id` が参加者を指す）でフロアをまたいで持ち越している。敵が置いたトラップはここに入れず、戦闘中の状態異常としてだけ扱えるかを確認する

## 4. データ構造

### 4.1 ドメイン（`server/domain/quest/`）

- `ProgressionType.Mirror = 2` を追加。`QuestStageDefinition.IsMirror` を追加
- `MirrorEnemySnapshot`：仮の敵ID（`QuestEnemyDefinitionId`）・元プレイヤーID・名前・画像・職業・レベル・転生回数・ステータス・技ID一覧。`ToEnemyDefinition()` で `QuestEnemyDefinition` を作る
- `MirrorFloorPlan`：フロア番号・ボスか・配置（仮の敵ID と位置）の一覧
- `MirrorEnemyPlan`：`MirrorEnemySnapshot` の一覧＋`MirrorFloorPlan` の一覧。`QuestRun` に null 許容で持たせる
- `MirrorCandidate`：候補プレイヤー（装備込みの実効ステータスと戦闘指数を計算済み）
- `MirrorEnemyPlanBuilder`（DB に触らない純粋なロジック）：候補・自分・フロア定義を受け取って `MirrorEnemyPlan` を作る。2章のルールは全部ここ
- `MirrorJobRowPolicy`：職業→希望列
- `QuestEnemyState.ReviveUsedCount`：そのフロアで蘇生技を使った回数
- 仮の敵ID：1,000,001 から登場順に採番（ラン内で一意であればよい）

### 4.2 アプリケーション（`server/application/quest/`）

- `IMirrorCandidateRepository`：上位20人＋同点分のプレイヤーID、技セット込みのプレイヤーを返す。`IPlayerRepository.GetPlayersAsync` は技を読まないので、敵の組み立てには使わない
- `QuestMirrorEnemyPlanService`：候補のプレイヤーと装備から実効ステータス・戦闘指数を出し、`MirrorEnemyPlanBuilder` に渡す
- `QuestRoomService`（開始処理）：Mirror のとき、味方を NPC テンプレートで補充 → 敵の候補を取得 → `MirrorEnemyPlanBuilder` → `QuestRunFactory` に計画を渡す
- `QuestRoomService`（ルーム作成）：Mirror で Multi なら拒否
- `QuestRunFactory`：Mirror の1階を計画から作る
- `QuestRunService.TryResolveIfReadyAsync`：Mirror のとき、敵定義と次フロアを計画から作る。捕獲は無効
- `QuestResponseMapper`：敵定義を計画から引く。ランの `floor` に `isMirror` を足す
- `QuestBattleFactory`：Mirror のとき敵の行動を `MirrorEnemyActionPolicy` で選ぶ
- `RankingAggregationService.BuildQuestClearCountAsync`：Mirror ステージのランを除外

### 4.3 DB（マイグレーション）

- `internal.quest_runs.mirror_enemy_plan_json`（jsonb、null 許容）：`MirrorEnemyPlan`
- `internal.quest_run_enemies.revive_used_count`（int、既定 0）：そのフロアで蘇生技を使った回数。敵の行はフロアごとに作り直すので、フロアをまたいで残らない
- `quest_run_party_snapshots` は変更なし。`quest_run_enemies.enemy_definition_id` には仮の敵ID が入る

## 7. マスタデータ（ステージング用シート）

- `stages`：id＝次の番号、`stage_code`＝`meikan-shrine`、`name`＝名鑑の祠、`battlefield_image_path`＝`image/quest/mirror-shrine-battlefield.svg`、`recommended_level`＝100、`minimum_entry_level`＝100、`min_party_member_count`＝4、`max_party_member_count`＝4、`is_active`＝true、`required_map_unlock_flag`＝空、`progression_type`＝Mirror
- `stage_floors`：1〜4F が Normal、5F が Boss。`exp_rate`・`gold_rate` はすべて 0
- `floor_enemy_spawns`・`stage_equipment_rewards`・`stage_item_rewards`：行なし
- `stage_npc_templates`：味方が足りないときの予備として既存のテンプレを指定
- 列の追加なし。`MasterDataIntegrityTests` に「Mirror ステージは `floor_enemy_spawns` を持たない」「enemies.csv の ID は 1,000,000 未満」を追加
- シートは PR の中で変更する（コードが Mirror を読める前に変えるとデプロイ時の取り込みで失敗するため）

### 7.1 調整値（`mirror_configs`）

敵の選出と行動の数値は、コードの定数ではなくマスタデータで持つ。エンドレスの `endless_configs` と同じく、`stage_id` ごとに1行。Mirror ステージに行がなければ起動時にエラーにする。

| 列 | 初期値 | 意味 |
|---|---|---|
| `stage_id` | 名鑑の祠の ID | 対象ステージ |
| `top_player_count` | 20 | 敵の候補にする上位の人数 |
| `enemies_per_normal_floor` | 5 | 通常フロアの敵の数（1〜6） |
| `boss_companion_count` | 3 | ボスフロアで自分と一緒に出る上位の人数（0〜5） |
| `max_normal_appearances` | 2 | 1人が通常フロアに出る回数の上限 |
| `max_total_appearances` | 3 | 1人がボスフロアを含めて出る回数の上限（`max_normal_appearances` 以上）。超える人はボスフロアに出さない。自分は通常フロアを「上限−1」回までにする |
| `second_choice_rate` | 0.15 | 第2候補の行動を選ぶ確率（0〜1） |
| `self_buff_rate` | 0.5 | 戦士系・魔法系が自分へのバフを使う確率（0〜1） |
| `self_harm_min_hp_percent` | 20 | 自傷バフを使える HP の下限（%） |
| `heal_hp_percent` | 50 | この HP（%）以下の味方がいれば回復を使う |
| `restore_mp_percent` | 30 | この MP（%）以下なら MP 回復を使う |
| `max_revives_per_floor` | 3 | 1フロアで敵1体が蘇生できる回数（0 以上） |

- コードに残すもの：職業ごとの行動の優先順（ロジックそのもの）、仮の敵ID の開始番号（1,000,001。DB の ID と衝突しないための技術的な値）
- 値はラン中に毎ターン読む（ラン開始時に固定しない）。シートを変えてデプロイすれば、進行中のランにも次のターンから効く
- 新しいタブは、PR の CI が本番用シートと照合するため、マージ前に本番用シートへ同期しておく
- 見出しだけの CSV は読み込みでエラーになるので、名鑑の祠の `stages` の行より先に、予定の ID（14）で初期値の行を入れておく。対応するステージがない行は使われない

## 8. テスト

- `MirrorEnemyPlanBuilderTests`：並び順（同点を戦闘指数で解決）、20人ちょうど／未満／5人未満、同じフロアに重複なし、通常フロア2回・合計3回の上限、ボスフロアに自分、自分が上位3人にいるとき、列のあふれ
- `MirrorEnemyActionPolicyTests`：職業ごとの優先順、各ガード（バフ重ねがけ・自傷・蘇生3回とフロアが変わったときの数え直し・即死除外）、守護系がかばうを最優先すること、HP が低い相手を狙う、乱数を固定したときの第2候補
- 戦闘：敵が挑発・かばう・トラップ・状態異常を使ったときに正しく解決されること
- サービス：報酬なし・捕獲不可・Multi 拒否・ランキング除外・ラン保存と復元（計画の JSON）
- フィクスチャ：`stages.csv`・`stage_floors.csv` に Mirror ステージの行を追加
