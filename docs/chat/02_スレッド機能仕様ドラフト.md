# スレッド機能仕様ドラフト

## 1. 目的

本ドキュメントは、既存のルームチャットとは別に、全プレイヤーが閲覧できるスレッド機能の要件と初期実装方針を整理するための仕様ドラフトである。

今回ユーザーから提示された要件は以下である。

* ルームチャットとは別にスレッド機能がほしい。
* スレッドはタイトル、本文、作成日時、作成者情報を持つ。
* スレッドには返信ができ、返信本文、返信日時、返信者情報を持つ。
* 各プレイヤーは最大 3 件までスレッドを持てる。
* 4 件目以降を作成した場合は、既存スレッドが削除される。
* スレッド一覧は全プレイヤー分を最新順で表示する。

## 2. 位置づけ

本機能は既存の `ChatRoom` ベースのルームチャットとは別用途である。

ルームチャット:

* 特定プレイヤーの部屋に紐づく時系列メッセージ。
* 所有者単位で閉じた履歴を持つ。

スレッド機能:

* プレイヤー本人が作成する公開トピック。
* 全プレイヤーの作成分を横断して一覧表示する。
* 1 スレッドに対して複数返信をぶら下げる。

このため、ルームチャットの `ChatRoom` / `ChatMessage` を拡張するのではなく、独立した集約として扱う前提で設計する。

## 3. 用語定義

### 3.1 スレッド

プレイヤーが作成する公開投稿の親データ。
タイトルと本文を持ち、0 件以上の返信を持てる。

### 3.2 返信

スレッドに紐づく子投稿。
本文を持ち、親スレッド配下に時系列で表示する。

## 4. 機能要件

### 4.1 スレッド作成

プレイヤーは新規スレッドを作成できる。

作成時に最低限必要な入力は以下とする。

* タイトル
* 本文

サーバーは作成時に以下を付与する。

* スレッド ID
* 作成者プレイヤー ID
* 作成日時

### 4.2 スレッド一覧

スレッド一覧には、全プレイヤーのスレッドを混在で表示する。

並び順は以下とする。

* 基本方針は「最新順」
* 一覧順は `created_at` 降順とする

一覧表示で最低限必要な情報は以下とする。

* スレッド ID
* タイトル
* 本文先頭 100 文字まで
* 作成日時
* 作成者情報
* 返信件数
* 最終返信日時

### 4.3 スレッド詳細

スレッド詳細では、親スレッド本体と返信一覧を表示する。

表示対象は以下とする。

* タイトル
* 本文
* 作成日時
* 作成者情報
* 返信一覧

返信一覧は少なくとも以下を持つ。

* 返信 ID
* 本文
* 返信日時
* 返信者情報

### 4.4 返信投稿

プレイヤーは任意のスレッドに返信できる。

初期実装では返信に対するさらに返信は扱わず、1 階層のぶら下がりだけを対象とする。

### 4.5 プレイヤーごとの作成上限

各プレイヤーが保持できる親スレッド数は最大 3 件とする。

4 件目を作成した時の基本方針は以下とする。

* 同一プレイヤーの既存スレッドのうち、作成日時が最も古い 1 件を削除する
* 削除対象スレッドに紐づく返信も合わせて削除する

## 5. 非機能・運用要件

### 5.1 公開範囲

初期要件上、スレッド一覧は全プレイヤーに公開される。

そのため初期実装では以下を前提候補とする。

* 認証済みプレイヤーは全スレッドを閲覧可能
* 作成者本人以外も返信可能
* 未ログインユーザーは閲覧不可とする

### 5.2 リアルタイム更新

本機能は初期段階では HTTP API + `useSWR` の再取得で十分とし、SignalR は導入しない前提候補とする。

これは AGENTS.md の「リアルタイム性が必要になった機能のみ SignalR を検討する」方針に合わせる。

## 6. ドメイン設計方針

### 6.1 新規集約候補

`server/domain/chat/` 配下、または必要に応じてスレッド専用名前空間配下に、以下の独立概念を追加する想定とする。

* `Thread`
* `ThreadReply`
* `IThreadRepository`

責務の想定は以下である。

`Thread`

* タイトル、本文、作成者、作成日時を保持する
* 返信コレクションを保持する
* 返信追加を制御する

`IThreadRepository`

* スレッド一覧取得
* スレッド詳細取得
* スレッド保存
* プレイヤー別スレッド件数確認
* 上限超過時の削除

### 6.2 作成者情報の扱い

「作成者情報」「返信者情報」は、現行チャット実装との整合上、少なくとも以下を表示対象とする。

* プレイヤー名
* 画像パス

表示名と画像は投稿時に固定せず、表示時点の最新プロフィールを参照する。

## 7. データ設計方針

### 7.1 テーブル案

RDB で保持する場合、初期案は以下である。

* `internal.threads`
* `internal.thread_replies`

`internal.threads` の候補項目:

* `id`
* `author_player_id`
* `title`
* `body`
* `created_at`
* `updated_at`
* `last_replied_at`

`internal.thread_replies` の候補項目:

* `id`
* `thread_id`
* `author_player_id`
* `body`
* `created_at`

本文文字数制約の初期仕様は以下とする。

* タイトル最大 50 文字
* スレッド本文最大 500 文字
* 返信本文最大 250 文字
* 1 スレッドあたり返信最大 100 件

### 7.2 削除方針

プレイヤーの 4 件目作成時に上限超過分を自動削除する。

削除方式は以下を候補とする。

* 物理削除とする
* 返信含めて cascade 相当で削除する

ソフトデリートは、現時点では要件に含まれないため対象外候補とする。

### 7.3 手動削除

プレイヤーは、自身が作成したスレッドの詳細ページから手動で削除できる。削除は物理削除で、関連する返信も cascade 相当で一括削除する。API では `DELETE /threads/{threadId}` を用い、認証済みでかつスレッドの作者本人しかアクセスできないようにする。

## 8. API 方針案

初期 API 案は以下である。

* `GET /threads`
* `GET /threads/{threadId}`
* `POST /threads`
* `POST /threads/{threadId}/replies`
* `DELETE /threads/{threadId}`

必要なレスポンス要素の候補は以下である。

`GET /threads`

* スレッド一覧
* 一覧各要素に作成者情報、返信件数、最終返信日時
* 一覧各要素に作成者プレイヤー ID (`authorPlayerId`) を含める
* 本文は先頭 100 文字までを返す
* 30 件単位のページングとする

`GET /threads/{threadId}`

* 親スレッド本体
* 返信一覧
* 親スレッドと返信一覧の各要素に投稿者プレイヤー ID (`authorPlayerId`) を含める

`POST /threads`

* 作成済みスレッド詳細、または一覧再描画に必要な要素

`POST /threads/{threadId}/replies`

* 追加後の返信一覧、またはスレッド詳細

## 9. フロントエンド方針案

初期 UI は以下の構成を候補とする。

* スレッド専用ページ
* スレッド一覧
* スレッド作成フォーム
* `/threads/{id}` の詳細ページ
* 返信投稿フォーム
* スレッド一覧・詳細・返信一覧の投稿者アイコンから `/players/{authorPlayerId}/visit` へ遷移できるようにする

データ取得は既存方針どおり `useSWR` を優先する。

## 10. 対象外

今回の初期仕様では以下を対象外候補とする。

* スレッド編集
* 返信編集
* 返信削除
* 添付画像
* 返信への返信
* 通知
* 既読管理
* 検索
* ページング
* 通報やモデレーション

## 11. 確認事項

以下は実装着手前に確定が必要な項目である。

1. 自動削除されたスレッドに対する扱いはどうするか。
   * 完全削除とする。
   * 削除履歴や監査ログは持たない。

2. 一覧件数の扱いをどうするか。
   * 初期実装からページングを入れる。
   * 1 ページ 30 件とする。

3. スレッド詳細の表示導線はどうするか。
   * URL で `/threads/{id}` のように詳細ページを分ける。

4. スレッド作成権限の制約は必要か。
   * 認証済みなら誰でも作成可能とする。
   * レベルや状態による追加制限は設けない。

5. 返信上限は設けるか。
   * 1 スレッドあたり 100 件上限とする。

6. 返信上限に達した場合の挙動をどうするか。
   * 101 件目の返信は拒否する。
